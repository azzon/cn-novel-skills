## 三、检查点协议设计稿
**载体**：根目录 .progress.json（机器权威）+ pre-commit hook从文件系统实扫自动重算（**禁技能手写**——事故证明手写状态必腐烂）。

```json
{
  "max_chapter": 79,
  "count": 79,
  "next_chapter": 80,
  "volumes": {"卷1": [1,30], "卷2": [31,50], "卷3": [51,73], "卷4": [74,79]},
  "story_time": {"current": "<来自ledgers/时间线.md末行>", "as_of_chapter": 79},
  "last_commit": "2487154",
  "next_action": "pipeline-chapter 第080章(卷4)",
  "updated_at": "..."
}
```

**hook校验门**：
- A门（防重复写章）：章号已存在即FAIL；新章标题与既有章库标题级查重WARN→人工确认
- B门（防错放卷）：expect=volume_of(M, volumes)，不匹配即FAIL；落入卷间隙即FAIL
- C门（防时序倒置，账建好后硬化）：新章末场日期<已有最大日期且文件头无"插叙:"豁免即FAIL，走arc-restructure重编号

**continuation恢复自检（位置三问v2，机器坐标版）**——在现有三问（几点/情绪/进点）之前加硬三问：
1. 我写到哪：.progress.json.max_chapter vs 实扫max——不一致→先跑rebuild，禁写任何字
2. 下一章几号、属哪卷：next_chapter==max+1？由volumes区间得出卷号；story_time给出故事内当前时间
3. 上一章讲什么：末章尾部全文+圣经章摘要（建立后）

**顺手修复**：.pipeline_state.json退役（单一事实源=文件系统，状态文件一律派生+hook校验）。

## 四、git commit message作为状态载体的可行性
可行但只能做二级信源：311条中119条含章号(38%)、110条含卷标，≥3种格式变体；致命缺陷是**写作序≠阅读序**（重编号使历史信息全部失真）。规范化方案（值得做）：commit-msg hook强制格式`ch(\d{3})(r(\d{3}))?: 《标题》|卷N|(自由文本)`且校验NNN==staged文件名章号。此后git log可作.progress.json的交叉验证源（progress.last_commit与git log -1比对即篡改/漂移检测）。
结论：主指针=文件系统实扫+.progress.json；git log规范化后做审计trail。**恢复时模型需要的不是更多叙述，而是一个hook能校验、撒谎会被抓住的数字。**
