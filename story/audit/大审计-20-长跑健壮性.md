## 一、P0事故:G8跨章贴入门崩溃(当前瘫痪新章入库)

### 1.1 现象(实测)
```
$ python3 tools/gate_chapter.py new text/卷1/第025章.md
=== gate_chapter [第025章.md] PASS ===
Traceback ... File "tools/gate_chapter.py", line 36, in cross_chapter_dup
    for para in staged_paras:
NameError: name 'staged_paras' is not defined   → 退出码1
```
- `cross_chapter_dup()`(gate_chapter.py:36)引用了 `staged_paras`,但它只是 `main()` 的局部变量,函数形参名为 `staged_bodies`。**任何 `new` 模式调用必然崩溃**。
- 影响面:pre-commit hook 对新章恒走 `new` 模式(hook L53)→ `GATE_FAIL_ALL=1` → 拒绝commit;`pipeline.py done N`(未提交章,gate模式=new)同样被拒。**25章现状下每写一章必撞**。
- 引入点:2b96db0("大审计-18代码审查P0/P1全修复…G8段落切分死代码修复…双向测试通过")。ch25最后入库于d15604d(10:59),早于2b96db0(12:58)——**带病上线后还没有新章入库验证过**。

### 1.2 二次伤害:hook输出无归因
hook用 `grep '\[FAIL\]' /tmp/gate_ch_out.txt | head -6` 摘要,traceback不含`[FAIL]`字样→开发者看到的全部信息是:
```
  [FAIL] 韧性门未过:
```
**(空body)**。违反本库自己的"错误必须可归因"铁律,直接把开发者推向 `--no-verify`。

### 1.3 回归盲区(根因)
`tools/evals.py` 只覆盖 `check.py --metrics` 与 `gate_chapter.py --recompute`——**从不执行 `gate_chapter.py new <file>`**(G8/G9/G2b路径零覆盖)。所以"双向测试通过"的声明无法被机器证伪。

### 1.4 修复建议(两行级)
1. gate_chapter.py:36 `staged_paras`→`staged_bodies`(已在/tmp副本验证修复后G8正常工作:300章语料0.02s/命中0)。
2. evals.py增加用例:构造"staged章段落与存量章shingle相似>0.85"的最小对,断言`gate new`退出码1且输出含`[FAIL] G8`。hook层同时改为:gate异常退出(非1)时原样输出`tail gate_ch_out.txt`,不做grep过滤。

## 二、规模压力推演:300章/90万字

### 2.1 实测数据(/tmp副本,语料≈真实单章字数)

| 组件 | 25章现状 | 300章实测 | 1000章外推 | 瓶颈? |
|---|---|---|---|---|
| gate new(G5+G8全语料重建) | ~0.15s | **0.26s,maxRSS 28MB** | ~0.9s/约80MB | 否(O(N)但常数极小) |
| gate modified | ~0.1s | 0.18s | ~0.6s | 否 |
| check.py 单章 | 0.05s | 0.05s(与库规模无关) | 0.05s | 否 |
| scores全库回归(300×check) | ~1.2s | **4.8s** | ~16s | 否(周运维级) |
| structure_check | 0.02s | 0.04s | 0.15s | 否,但**只扫卷1**(见2.3) |
| gate --recompute | 0.02s | 0.02s | 0.05s | 否 |
| pipeline status | ~0.3s | **0.82s**(含301次`git status`子进程,每章1次) | ~2.7s | 临界,可批量化 |
| pre-commit批量k章 | — | **批10章=2.1s,边际约0.2s/章** | 批10≈7s | 批量>30章≈6-7s,开发者开始--no-verify |
| scores.json | 10.7KB | **129KB**(301章,每次done全量重写) | ~430KB | 否 |
| .progress.json | 0.35KB | ~0.4KB(含volumes) | ~0.5KB | 否 |
| ledgers合计 | 318行 | 线性外推约3.8K行/约300KB(时间线190B/行→57KB) | — | 机器读无压力;**人/AI逐章编辑成本线性涨** |
| 章摘要.md | 2.7KB | ~33KB | — | **无任何工具读它**(见2.4) |

**对题设的正面回答:G8语料线性增长是真实存在的(gate 0.15s→0.26s),但常数太小,300章单次commit的机器耗时不到1秒——commit不会被速度赶跑。**会被赶跑的是下述四件事。

### 2.2 真正的第一个瓶颈:注入预算(25章已击穿,300章前必崩)
`pipeline.py bundle 26` 实测(在/tmp副本):
```
6当前时刻卡: 934/500字 !   → 已裁剪:卷一收口指令③④⑤⑥被截断
8伏笔在跑项: 1435/600字 !  → 已裁剪:在跑伏笔丢失约6成可见性
```
- 时刻卡自身约束≤20行,但"未回收"清单+收口指令只进不出,AI维护者会持续膨胀→**上限被击穿时裁剪是静默的**(仅行尾一个`!`和正文内一个小tag)。
- 300章时若无强制归档纪律:伏笔在跑项、禁区、悬线都会数倍于今日,bundle第6/8项沦为"裁剪后的碎片注入",**续写穿帮从源头发生**——这比任何CPU问题早到两个数量级。

### 2.3 隐性覆盖缺口
- `structure_check.py` 缺省只扫 `text/卷1`(pipeline status接入时也不传参)→写到卷6时,**结构同构门对卷2-6永久失明**。
- pipeline status对每章spawn一次`git status --porcelain`(301次)→0.82s;1000章约2.7s,建议改单次`git status --porcelain text/`解析。

### 2.4 圣经与台账的"人肉瓶颈"
- 章摘要.md 300行=33KB,没有任何工具读它(bundle第7项只读全书卡+卷摘要-卷N.md;**卷摘要文件不存在**)。它是纯人肉账,300章时逐行核查不可行→必须靠机器门(见四、五)。
- rebuild技能假设"逐章扫描正文重导六账"=一次读入90万字(约120万+token),**单会话物理不可行**,技能无分卷/分块协议(见四)。

### 2.5 建议阈值(超出即运维动作)
| 指标 | 阈值 | 动作 |
|---|---|---|
| hook单章commit耗时 | p95≤3s | 超限=profile gate |
| hook批量commit | ≤10s或批≤15章 | 超批改分批+事后scores全量 |
| bundle任一项超上限 | >0项 | **视为FAIL级**:强制归档(收口指令→卷摘要,已回收伏笔出列) |
| gate单次 | ≤1s@300章 | 超限=shingle缓存化 |
| scores全库回归 | ≤30s | 周级跑,不进commit路径 |
| 时刻卡/伏笔在跑字数 | 500/600上限 | 超限改上限为硬门而非裁剪 |

## 三、断点恢复演练(会话压缩后新会话只拿三样东西写ch26)

输入:`pipeline.py status`输出+`ledgers/当前时刻卡.md`+`story/60-圣经/章摘要.md`。

### 3.1 四问作答
| 问题 | 可恢复? | 依据 |
|---|---|---|
| a) 下一章写什么 | **✓完备** | status"下一动作: pipeline.py next 26"+时刻卡"下一章:第026章(查抄余波+同行侧目·危机P3·苏棠送一碗面不说安慰话)"双源一致,且自带场景方向 |
| b) 上一章末拍与语气 | **△部分** | 时刻卡仅1字引文"怕。"（025）(该引文有6.6口供对账背书,可信);章摘要ch25行有"P4谷底;'怕。'"。但①**上一章末尾原文(900字)不在三样内**,在bundle第5项——continuation自己的"原文喂养法"宣称90%连贯还原靠原文,三样东西恰好缺它;②完整声纹行(出场者过滤版)在bundle第3项,时刻卡只有1行8人速记;③status**不输出**末拍/声纹/冷读欠账以外的任何语气提醒 |
| c) 知情状态(谁知道什么) | **✗完全缺失** | 三样里无一处"知情状态";它只存在于场景卡(未填)与大审计-15(一次性文档)。时刻卡"禁区:先知不外露"仅部分代偿。**这是跨会话穿帮的最大敞口** |
| d) 禁区 | **✓完备** | 时刻卡禁区行6条(先知/年代/曹三不洗白/苏棠心动/黑柜台/涨价联手不复用) |

### 3.2 恢复链路缺口清单(按严重度)
1. **知情状态无台账、无bundle注入位**(bundle 11项里没有知情快照)→新会话只能靠重读上一章猜。
2. **bundle第7项是污染源**:实测注入的书卡内容为"进度: 0章(立项完成,开写卷一)/章级摘要: TODO"——**全书卡自立项后从未更新**(实际25章),且`卷摘要-卷1.md`不存在时代码静默跳过(347/700字,半空注入)。新会话拿到的"圣经"与status(25章)自相矛盾,却无任何告警。
3. **时刻卡新鲜度检查装反了方向**:done 6.5只在"写完之后"软提醒时刻卡未含本章;status/next(写前)不检查。若上个会话死在"commit后、时刻卡更新前",新会话在写前阶段得到的是过期时刻卡且无感知。
4. **章摘要无机器校验**:漏写某章一行、或与story-bible技能约定的文件名(`卷N章摘要.md`)漂移(实际是单一章摘要.md),都没有任何门。
5. status的"下一动作"没有指向continuation技能/三问协议——机器不会提醒新会话走恢复仪式,依赖模型自觉。

## 四、状态一致性:三种损坏演练(全部在/tmp副本执行)

| # | 损坏注入 | 机器表现 | 自愈? |
|---|---|---|---|
| A | 删除`.progress.json` | status照常工作(文件系统权威;仅"故事时间"行消失,无"缓存缺失"提示);任意章节commit时hook自动`--recompute`+`git add`;手工`--recompute`秒级重建,内容与原件一致 | **✓完全自愈**(全系统唯一) |
| B | 当前时刻卡:上一章末拍改为伪造引文"天亮了。"（099）(第099章不存在),"下一章"改为第099章 | `done 25 --revise`**零警告通过**(实测)。6.6口供对账逻辑:`cm.get(099)=None`→静默跳过——引文校验只对"存在的章"生效;"下一章"字段无任何门;6.5因卡内含"第025章"字样照过 | **✗不可自愈** |
| C | 时间线砍掉最后3行(ch23/24/25) | `--recompute`把`story_time`回写成"第022章·2006-01下旬"并写入progress(**缓存投毒**);status随后展示错误故事时间,零告警;新章26过G6时序门(tl_max=22<26);done的七账盖章只能抓"当前章行缺失"(WARN不阻断),**历史行缺失永不可见**。时刻卡(3月)与progress(1月)两个注入源互相矛盾也无人对表 | **✗不可自愈**,需人工rebuild |

### 不可自愈点汇总(带根因)
1. **时刻卡无重建脚本**:rebuild技能是AI手工流程,无工具支撑;B类坏引用(指向不存在章)在机器层零检出。
2. **圣经三件套零校验零重建**:全书卡实测已烂("进度0章"实为25章,却是bundle的常驻注入物);章摘要漏行无门;卷摘要从未生成。
3. **时间线只查max章token**:done盖章仅验证"第N章"字样在文件中,历史区间覆盖不做对表;recompute还会把残缺时间线的结论传播进progress。
4. **六账(伏笔/梗/钩分布/类型轮换/人物状态/线弦)无重导工具**:rebuild技能假设全稿一次可读——300章/90万字单会话约120万+token,物理不可行,**技能缺"分卷重导协议"**(每卷扫一遍→卷内对账→卷间合并),这是300章时rebuild不可执行的根因。
5. **evals基线不含gate new模式**:G8类"带病上线"还会复发(1.3节)。

## 五、钩子可靠性(依赖与环境)

| 场景 | 实测/推演 | 后果 | 建议 |
|---|---|---|---|
| 无python3(仅python/无别名) | /tmp/fakebin实测:gate与check全部"env: python3 not found"→127 | fail-closed但**FAIL原因全部隐形**(错误文本不含[FAIL],grep后输出空body);开发者两次遇到必--no-verify | hook开头`command -v python3 >/dev/null || { echo "[FAIL] 缺python3…"; exit 1; }`;并输出gate原始tail |
| /tmp硬编码路径(gate_ch_out/check_out/gate_git_err) | 多worktree/并行commit互相覆盖摘要 | 间歇性错误报告 | `mktemp`或以REPO路径哈希命名 |
| commit-msg hook无自动同步 | `pipeline.py sync_hooks`只同步pre-commit(L206-217);全库grep证实无任何工具装commit-msg | 新clone/重装后**静默失效**→"commit-msg含章号"的git-log二级信源断裂 | sync_hooks扩展到commit-msg |
| 章号提取`grep -o '[0-9]*'` | `第26章.md`(2位非规范命名)→CH_NUM=26→`ls text/卡/*第26章*`匹配不到0填充卡 | 卡门/waiver误报"无场景卡" | gate已有卷名规范门,建议文件名同样归一(警告级) |
| BSD/macOS `find -regex`(E节) | GNU语义,BSD下语法不同 | 每10章drift提醒可能静默不触发 | 改用`git ls-files 'text/卷*/第*章.md' \| wc -l` |
| hook内`git add .progress.json` | pathspec式commit(`git commit -- <file>`)时index与提交内容可能错位 | 低危,progress可能滞后 | 可接受,文档标注即可 |
| 批量commit>30章 | 300章时约6-7s | 触发--no-verify习惯化 | hook对NEW>15章打印"批量模式:建议分批,或--no-verify后补scores全量" |
| 大diff性能本身 | 0.2s/章边际,300章批10=2.1s | — | 无需改 |

**结论:hook不会被时长禁用(300章单章commit<1s),会被"不可归因的FAIL+环境脆弱"禁用。**

### 最该自动化的1项
**圣经三件套+时刻卡的"写前新鲜度门"**:
- status/next(写前):校验`当前时刻卡.md`含第N章(新鲜)、`章摘要.md`含1..N全行、`卷摘要-卷N.md`存在、全书卡"进度"字段=实扫max;任一不满足→打`[REMIND] 恢复链路数据过期→story-bible/timeline-keeper`。
- done(写后):把上述从"无"升为硬约束(现仅时刻卡一条软门)。
理由:它是断点恢复链路的地基,却是全系统唯一零机器校验的常驻状态;25章就已出烂账(全书卡),300章必崩。实现只需pipeline.py加~40行,无新依赖。
